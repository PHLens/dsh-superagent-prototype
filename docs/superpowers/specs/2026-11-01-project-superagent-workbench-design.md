# 项目型 Superagent 工作台：产品与架构设计

日期：2026-11-01（Asia/Shanghai）

状态：设计讨论已确认，书面规格待用户评审；本文件不授权直接实施。

适用范围：个人使用、单台常驻 Mac、多个项目、Tailscale 私有访问。

## 1. 目标与已确认选择

用户以项目为单位与长期协作者对话，由系统安排和恢复后台任务，无需管理 worker Session。项目可以同时包含研究、代码、实验和文档工作，GitHub 仓库是项目资源之一。

已确认的产品选择：

1. 统一首页展示多个项目和待决事项；先进入项目，再与该项目 Superagent 对话。
2. 每项目一个主对话；任务独立跟踪；资料、成果和项目约定有独立入口。
3. 新建项目只要求名称和一句目标；通过对话逐步补齐资源与约定。
4. KORAM 是一个研究项目，研究与代码工作共同属于该项目，不按工作类型另建项目。
5. 采用“讨论后执行”：确认目标与方案后自主推进，超出授权范围时再询问。
6. 项目使用独立工作空间，关联已有代码仓库和资料目录，不要求搬迁或重排已有资源。
7. Web、数据库、项目文件和执行服务都运行在 Mac；经 Tailscale 私有网络访问。
8. 接受 Mac 离线时工作台和机器人暂时不可用，不建设云端离线收件箱或执行节点。
9. 一个飞书机器人，以与用户私聊为入口，跨项目通知并处理回复；创建项目不创建机器人或群。
10. 暂停、任务确认、待决问题和必要执行状态持久保存；恢复时核对现场，避免盲目重跑。

首版以适配手机的 Web 为完整工作台。独立 App、公网域名、Cloudflare Tunnel、云端控制台、多人协作和多机调度不属于首版。

## 2. 当前原型的复用与改动边界

原型可以复用的机制包括 Ticket、Assignment、Input、Attention、持久 Effects、执行槽、DSH Session 管理、报告与恢复、Source/Channel 适配和现有管理面板组件。产品任务可以沿用 Ticket 的执行身份，不另造一套互相独立的任务引擎。

需要实质调整的单项目假设：

- [deployment.ts](../../../src/deployment.ts) 的部署级单一 GitHub repository 与 GitHub 账号就绪要求。
- [setup.ts](../../../src/app/setup.ts)、[runtime.ts](../../../src/app/runtime.ts) 的全局 setup 门禁和单一 masterId。
- 执行环境、prepare、提示词、报告工具中默认面向单仓库和 PR 的约定。
- Source 入口、Thread 订阅与通知缺少可靠的项目归属。
- 管理 HTTP 的本机 Host/Origin 限制，以及缺少项目对话和项目创建流程。

不能通过仅增加项目列表或给 Ticket 添加一个字段完成改造。项目上下文必须贯穿入口、对话、工具、执行环境、报告、文件与通知。

采用 fork 上原生多项目的路线，继续运行于 DSH。每项目一个 Superagent 是逻辑身份，不要求每项目一个 DSH 进程或独立部署。

## 3. 第一版范围与交付顺序

第一版交付一条完整的个人使用流程，按依赖拆成三个可验收增量：

| 增量 | 交付能力 | 退出条件 |
| --- | --- | --- |
| 1：项目基础 | 项目创建、独立工作空间、资源关联、项目知识与任务归属；无 GitHub 也能进入对话 | 两个项目的资源、上下文、任务查询和工具调用不会混用 |
| 2：Web 协作闭环 | 项目主对话、方案确认、执行、待决事项、成果与追溯；手机远程访问 | KORAM 的一个小型研究验证任务可以从讨论推进到交付 |
| 3：飞书私聊闭环 | 单机器人跨项目通知、回复关联、显式项目的新需求、消息去重 | Web 确认任务后，可从飞书回答问题，结果在 Web 同步可见 |

启动恢复、持久化、备份和恢复验证随相关增量一起交付，不延后为独立的可靠性补丁。新工作台稳定前，现有 KORAM 服务继续使用旧部署；开发配置保持隔离。

首版不包含自动推进新的研究方向、全局对话自动猜测项目、复杂任务树、可视化流程编排、自动合并 PR、自动发表研究结论和任意外部动作的精确一次执行保证。

## 4. 用户体验与导航

### 4.1 首页

首页优先呈现“待我处理”，再展示项目列表。每个项目显示名称、目标摘要、当前任务摘要、最近活动与阻塞情况。健康状态需反映实际已知信息；不将最后一次上报伪装成实时进度。

首页支持创建项目。任务执行细节和原始 Session 列表不作为默认首页内容。

### 4.2 项目页面

每个项目有四个主要入口：

- 对话：持续讨论、提出需求、确认方案、询问进度。
- 任务：查看排队、执行、待决、失败、暂停和已结束的工作。
- 资料与成果：访问项目文档、实验记录、交付物与关联资源。
- 项目约定：目标、假设、已确认决策、资源位置和执行规则。

主对话中的重要消息展示任务归属。任务详情收敛该任务的方案、进展、待决问题、成果与执行历史。任务详情可以提交补充信息，并与项目对话共享同一条规范化记录，不复制成两份独立历史。

没有连接仓库或配置执行环境的项目仍可讨论、保存资料和形成方案；只有需要相应资源的任务等待补齐配置。

### 4.3 移动端

首版适配窄屏浏览器，优先保证进入项目、对话、确认方案、处理待决问题和查看成果摘要。详细日志、复杂设置与大文件分析允许使用桌面端，主要流程不依赖鼠标悬停或横向大表格。

## 5. 概念模型与归属不变量

| 实体 | 职责 |
| --- | --- |
| Project | 稳定身份、名称、目标、工作空间、约定和资源集合 |
| ProjectConversation | 项目的主对话及跨入口可追溯的消息记录 |
| ProjectKnowledge | 经确认的事实、决策和约定，以及带来源的假设与研究材料 |
| PlanRevision | 不可变的方案版本，包含目标、范围、产出、资源、成本限制与完成标准 |
| Authorization | 用户对具体方案版本或明确操作范围的确认记录 |
| Task / Ticket | 可跟踪的工作目标及其生命周期；每个任务只属于一个项目 |
| Assignment / Execution | 某次执行尝试、执行输入、运行状态与报告 |
| Attention | 需要用户处理的问题、上下文、处理状态和关联任务 |
| Resource | 仓库、目录、数据或其他已登记资源及其使用约定 |
| Artifact | 交付物的路径或引用、所属任务、依据、生成版本与有效性信息 |
| ChannelMessage | Web/飞书消息的原生标识、规范化内容、回复关系与项目/任务归属 |
| Delivery | 待发、已发或失败的通知及关联事项 |

必须保持以下不变量：

- 项目 id 稳定，不随显示名称和目录名变化。名称相同或别名冲突时，不静默选择项目。
- 任务、方案、授权、执行记录和成果均具有明确的项目归属。
- worker 的项目身份由服务端任务上下文固定，不能靠模型随意传入 projectId 切换。
- 所有任务查询、工具资源读取、成果写入与回传都校验项目归属。
- 未绑定项目的私聊新消息可以暂存并询问归属，在归属明确前不派发 worker。
- 一个任务可以包含调研与代码步骤；仅在独立验收、并行或恢复边界需要时拆分任务。
- 项目主对话是产品记录，不等于永久增长的单个模型上下文。底层执行 Session 可以整理或重建，项目身份和可追溯记录保持连续。

## 6. 方案确认与自主执行

研究方向、关键科学判断和阶段性选择由用户主导。Superagent 可以按请求整理证据、比较方案和形成可执行建议；对于明确授权的调研操作，无需逐工具再次确认。

实施前保存方案版本，至少包含：目标、范围、预期产出、资源与环境、完成标准，以及会影响选择的成本或限制。用户通过 Web 或飞书说“按这个方案做”即可确认，不重复要求按钮确认。

确认必须能唯一关联到方案版本。若已存在多个候选方案或用户表述不清，先澄清；不将一条普通赞同消息扩展为对后续所有动作的授权。

范围内步骤自主推进。新增资源权限、改变研究方向、扩大数据范围或明显超出约定成本等变化需另行确认，并保留版本关系。现有授权不会被模型自行扩张。

引用此前已确认方案的明确执行指令可以直接开始，不强制重新讨论。普通进展默认留在任务详情，关键决策和阻塞才请求用户介入。

## 7. 生命周期与完成标准

面向用户的基本状态与服务端的执行尝试分离：

| 状态 | 含义及主要转换 |
| --- | --- |
| 方案待确认 | 尚无实施授权；确认后排队，修改产生新方案版本 |
| 排队 | 已授权，等待资源或并发槽；显示具体等待原因 |
| 执行中 | 当前存在有效执行尝试或其恢复核对过程 |
| 需要你决定 | 有阻塞执行的 Attention；回复被持久接收后，根据内容继续或修改方案 |
| 执行失败 | 本次尝试无法完成；保留现场、原因与可选重试入口 |
| 暂停中 | 已收到暂停指令，不分配新步骤，当前操作正在安全收束 |
| 已暂停 | 已达到安全检查点，不再推进；收到明确恢复指令后才继续 |
| 已停止 | 当前任务结束；保留记录与成果，后续需求可以新建关联任务 |
| 已完成 | 满足该任务事先约定的交付标准 |

暂停不代表瞬间冻结任意 shell 或外部操作。不能安全打断的步骤采用检查点暂停，收束完成后才显示“已暂停”。用户暂停意图必须跨重启保持，不能因服务恢复自动解除。失败后的重试保留原任务身份与授权，创建新的执行尝试；若超出原授权则先确认。

不阻塞已授权任务的研究判断可以单独留在项目待决事项中，不强制将已完成任务改成等待状态。重新核对现场时显示“核对中”提示，在明确结果前不派发可能重复的操作。

“Mac 离线”是运行环境情况，不是所有任务自动失败。在全本地架构下，远程页面本身可能不可达；重新访问后再核对未结束任务，不伪造离线期间的新状态。

完成标准按任务确定：

- 调研：来源可核验，比较与结论有边界。
- 开发：实现符合约定，相关检查通过，交付可审阅变更；PR 由人合并。
- 实验：代码版本、配置、数据引用、运行记录和结果可追溯。
- 分析：区分观察、解释、假设及尚未验证的推断。

代码实现正确、实验有效完成、结果支持研究假设，是不同判断。任务交付完成不自动代表研究方向已证实。

## 8. 工作空间与文件规则

项目工作空间使用稳定 id 定位；界面可展示友好名称。以下为逻辑结构，不要求搬迁已有仓库：

```text
<workspace-root>/<project-id>/
├─ project/          # 目标、假设、约定、已确认决策
├─ research/         # 文献笔记、调研与比较
├─ experiments/      # 实验方案、运行清单、结果与分析
├─ outputs/          # 整理后的报告、图表、文稿
├─ tasks/            # 可阅读的方案、任务说明和成果索引
└─ .superagent/      # 项目标识、资源关联和运行索引
```

资源登记使用稳定 resourceId、类型、规范化路径和用途；已有 KORAM 仓库保持原位。资源关联默认使用登记引用，不要求创建符号链接或复制仓库。

应用数据库是项目元信息、对话、任务、授权、Attention、通知与关联关系的权威记录。工作文件是研究内容和成果的实际载体；项目知识记录其来源、确认状态和文件版本。可阅读的任务说明由数据库导出，不作为第二套运行状态。

用户手工修改文档时，保留文件变更，在读取或显式刷新时检查知识索引；新增内容不自动视为已确认决策。已确认决策在数据库中保留不可变版本和来源消息，文档展示可追溯的导出或引用。首版不要求向量数据库、全盘索引或常驻文件监视器。

并行任务使用独立工作区。代码任务使用独立检出或 worktree，实验和调研使用任务级工作目录。交付时登记成果清单与依据，原子更新清单，不互相覆盖共享结果。

DSH 原始 Session 保持其原生存储机制，通过项目、任务和执行记录索引；首版不承诺将 Session 数据库物理搬入各项目目录。关联工作区之外的仓库和数据必须单独纳入备份范围说明。

远程资料和成果通过已认证的应用接口访问，使用 projectId、resourceId 或 artifactId 定位，不依赖浏览器打开 Mac 的本地文件路径。文件接口校验登记资源、规范化后的真实路径与访问范围，拒绝路径穿越或符号链接越界。首版支持目录浏览、文本/Markdown 查看与文件下载；大型二进制及专用格式可以下载到本机查看。

## 9. 飞书私聊与 Web 的统一记录

### 9.1 入口定位

一个机器人服务多个项目，只允许已配置的用户发起工作。项目创建不新增飞书应用、机器人或群。

首版保留一对一私聊；项目群绑定和团队协作延后。私聊接收依赖 Mac 服务在线，不依赖手机已连接 Tailscale；打开 Web 详情需要连接 Tailscale。

首次绑定通过授权用户主动私聊机器人，登记机器人身份、用户 openId 与 DM chatId，并验证机器人可以向该私聊主动发送消息。未建立私聊或权限不足时，Web 明确展示通知未就绪，不将其视为已投递。

现有 [feishu-channel.ts](../../../src/sources/feishu-channel.ts) 只能回复已有 messageId，且返回 sent/gone，不足以承载从 Web 发起任务的主动通知。需要扩展出主动私聊发送和原生投递回执，持久保存 Delivery → 原生机器人 messageId → projectId/taskId/attentionId/planRevision 的映射，作为后续回复路由依据；不依赖模型从通知文本反推归属。

### 9.2 确定性归属

消息路由按以下顺序处理：

1. 回复已知通知或任务消息：通过原生 messageId、回复链和通知记录找到项目、任务或 Attention。
2. 明确项目的新消息：解析用户给出的项目名或别名，唯一匹配后进入项目主对话。
3. 仍存在多个候选或完全没有项目：保存消息并询问归属，明确后继续原输入，不要求重发全文。

不得把“上一次聊天的项目”作为无提示默认值。回复链指向的项目与正文显式指定的项目冲突时先询问，不静默采用任一方。不能仅根据整段私聊的 Thread 归属将后续消息广播给多个项目 worker；现有原型的 Thread 订阅需要适配到逐消息的明确关联。系统提供给项目协调者和 worker 的私聊历史也按已确定归属过滤，不将整段跨项目私聊当作任务上下文。

明确项目名不等于实施授权。新需求仍按讨论与确认规则处理；对唯一、已确认方案的执行指令可以直接形成任务。

### 9.3 通知与待决事项

默认通知：需要决策或补充信息、任务完成且有成果、无法自行处理的失败或阻塞。每条通知标明项目与任务，并提供摘要和可访问的详情链接。

Attention 的处理状态独立于通知投递状态。通知发出不等于用户已处理；回复只有在服务端持久保存并关联正确问题后才标为已接收。未解决的问题持续保留在首页，不靠重复刷屏维持存在感。

Web 和飞书写入规范化消息记录，保留原生来源与回复关系。机器人自己发送的通知不重新变成用户任务，跨渠道同步不形成回环。通知模板和确认提示首版可用文本实现，不依赖交互卡片。

## 10. 单 Mac 架构与组件边界

```text
手机 / 其他电脑
        │ Tailscale 私有网络
        ▼
Tailscale Serve（HTTPS）
        │ 本机转发
        ▼
DSH Web + Superagent fork
  ├─ 项目工作台与项目对话
  ├─ 项目目录、知识与资源服务
  ├─ 任务、授权与待决事项
  ├─ Source 入口与飞书路由
  ├─ Effects / Outbox / 调度
  └─ DSH Session / worker 执行
        │
  本地数据库、工作空间、关联资源
```

组件职责：

- 项目服务负责项目身份、约定、资源和上下文组装，不直接运行任务命令。
- 对话入口负责持久接收、身份校验、项目/任务归属和展示；不自行决定外部副作用。
- 项目协调者负责讨论、形成方案、提出任务与处理已归属输入；不同项目不共享未筛选的完整上下文。
- 任务引擎负责授权约束、状态转换、Assignment、Input、Attention 与恢复决策。
- 执行适配器负责在固定项目上下文中准备工作区、启动或恢复 DSH Session、报告结果。
- Source/Channel 负责飞书或 GitHub 的原生接收、回复与链接，不持有项目研究判断。
- 存储与成果服务负责事务记录、文件索引、通知交付状态和备份接口。

各项目协调者按需唤醒，采用项目级串行处理避免确认与消息竞态；worker 可以在实例总并发限制内执行。总并发和各项目占用在任务层可见，不为每个项目预留永久占用模型的会话或进程。

项目运行上下文固定包含 projectId、taskId、planRevision、authorizationId、资源引用和工作区。项目间隔离由服务端归属检查、工具上下文和工作区规则实现。现有 worker 以用户 OS 身份运行，逻辑归属检查不等于 OS 文件沙箱；首版不宣称抵御任意进程访问其他用户文件。

## 11. GitHub 和能力解耦

实例启动只依赖基础存储与 DSH 环境，不要求所有项目配置 GitHub。某个项目未连接仓库或凭证失效，只阻塞需要该资源的工作，不阻塞其他项目或项目讨论。

GitHub 账号可以实例级登记并由多个项目引用；repository、prepare、git 工作区和代码交付约定按项目/任务资源解析。工具 schema 和提示词不能无条件读取部署级 GitHub 登录身份。

研究、文档和代码能力通过任务所需资源与交付标准组合，不设计互斥的项目类型。PR 信息是可选的代码交付扩展，非所有任务报告的必填内容。

沿用用户现有代码约定：人合并 PR；代码提交作者采用已确认身份。研究结论与对外发布不会因任务完成自动获得授权。

## 12. 私有远程访问

保持 DSH 后端监听本机，通过 Tailscale Serve 暴露 tailnet 内的 HTTPS 入口，不启用公网 Funnel。

接入需明确配置唯一受信任的外部 origin，同时保留 DSH 登录认证、浏览器来源校验和请求保护。代理相关头只在固定本机代理入口的边界内使用，不任意信任客户端传入的转发身份。

现有仅允许 localhost 的 Host/Origin 校验必须适配；只改 Host 不能处理 HTTPS 外部 Origin。实现阶段同时检查 DSH 本身的认证、Cookie、WebSocket/流式连接和资源 URL，不能以首页返回 200 代表全部管理功能可用。

验收从真实 tailnet 设备访问，覆盖项目对话、保存、任务操作、实时进展和重新连接；错误来源的写请求仍应被拒绝。Mac 离线时显示明确连接失败，不显示虚构的持续在线控制台。

## 13. 持久接收、幂等与恢复

对 Web 输入使用稳定的客户端操作 id，对飞书输入使用原生事件/消息 id。服务端事务保存输入、归属、授权或待决状态及后续 Effects 后，才确认已持久接收。重复提交返回已有结果或继续其处理，不产生第二个任务。

数据库事务不与外部副作用组成一个原子事务。外部操作采用执行标识、先查后做和结果记录降低重复风险；不能确认结果时进入核对或待决状态，不声称普遍的精确一次执行。

飞书投递使用稳定幂等键。若消息发送成功但原生 messageId 映射尚未落盘即退出，恢复时需通过幂等结果或消息查询补齐映射；无法确认则标记投递待核对。收到尚无可靠映射的回复时保存并核对，不把它当作另一个项目的新任务。

重启流程：

1. 获取状态目录锁，打开数据库并检查版本，恢复必要组件。
2. 加载用户暂停状态和未结束任务；保留当前授权与待决问题。
3. 核对 DSH Session、仍存活的子进程、文件与外部操作结果。
4. 已完成部分登记并复用；可恢复部分产生接续输入或新执行尝试。
5. 不确定或有重复副作用风险的部分请求复核，不盲目重新执行。
6. 重建未完成的通知与交付队列，去重后继续发送。

网络故障与任务失败分开记录。保留最后已知事实和核对时间；恢复过程对用户显示“核对中”，不得直接把旧的“执行中”当作当前事实。

## 14. 启动、备份与恢复

使用 macOS 服务管理机制保证 DSH 与 Tailscale/Serve 所需组件在预期运行环境中启动；服务异常退出可自动恢复，主动停止意图应保留。来电自动开机不等于服务自动就绪，需实际验证登录、磁盘解锁和运行环境条件，不默认修改系统安全设置。

实例保持单写者，避免旧实例与开发实例同时写同一状态目录。运行期间不以直接复制活跃 SQLite 主文件作为完整备份。

备份包含：

- 应用数据库的一致性快照、schema 版本与恢复说明。
- 项目工作空间、附件和已登记成果。
- 恢复执行所需的 DSH 状态、项目/任务/Session 映射与配置。
- 关联仓库、未提交工作和外部数据的覆盖清单；已在其他位置保护的资源明确列出恢复位置。
- 凭证单独加密备份，不写入代码仓库或可公开的项目文档。

恢复点包含备份清单，记录应用与 DSH 状态版本、文件版本或校验信息以及备份边界。实现需要协调数据库快照与仍在写入的文件；必要时在安全检查点短暂收束写入。不能确认一致性的备份标为未完成，不显示为可完整恢复。

默认目标是每日一份完整恢复点、保留最近七份，至少有一份独立于该 Mac；升级和迁移前额外生成恢复点。备份目的地在本机设置中由用户连接，未配置或最近备份失败时明确显示。该默认值是首版建议，允许用户调整。

必须做一次到隔离目录的恢复演练，验证项目、对话、任务、授权、待决事项、成果链接与必要 Session 映射可以读取。恢复实例默认禁止外发和执行，防止恢复演练重放任务。

## 15. 开发隔离与现有 KORAM 迁移

设计文档保存在现有上游检出中，便于先评审；创建 fork、选择仓库名称和配置开发实例属于后续实施准备，本轮不执行。

新版本使用独立 profile、状态目录、工作空间根和端口。现有 KORAM 服务继续运行稳定版本，开发阶段默认关闭新实例的飞书接收和外发。

正式接入现有机器人时只有一个活动消息接收与路由服务。切换前清点旧任务，完成或明确暂停；生成备份，记录可回退配置。不得用两个未协调实例共同消费同一机器人作为项目路由方案。

新 KORAM 项目关联现有仓库，导入用户核对过的目标、约定和必要决策。首版不自动搬迁全部历史 DSH Session 或推断所有旧任务归属；旧状态保留并给出读取方式。若需要完整历史迁移，应另列迁移规格，不在切换时临时猜测。

验证新闭环后再停用旧服务；回退先停新入口，再恢复旧入口，避免重复接收或并行写入。

## 16. 验收与验证策略

### 16.1 端到端场景

1. 从手机经 Tailscale 创建一个只有名称和目标的项目，立即开始对话，无 GitHub 也能保存。
2. 创建 KORAM 与另一个项目，分别关联资源；消息、工具调用、任务与成果不串项目。
3. 在 KORAM 讨论研究假设并确认一个小型验证方案，包含必要调研、代码或实验步骤。
4. 在既定并发限制下执行，产生明确的代码/实验版本记录和成果索引。
5. 阻塞问题进入首页并私聊通知；飞书回复后在同一任务中继续，Web 可追溯该回复。
6. 飞书新消息明确项目后进入讨论；未指明项目的消息先询问，不默认沿用上一个项目。
7. 飞书事件重投、Web 超时重试和相同确认重发不产生重复任务或重复授权。
8. 服务重启后先核对未结束工作，复用已有实验或 PR；无法确认时不重放危险操作。
9. 用户暂停跨重启保持，停止任务不会因普通渠道重连自动复活。
10. 任务交付后可以从成果追溯到任务、方案版本、相关来源或代码与运行配置。
11. 关闭浏览器不影响执行；Mac 离线时入口确实不可用，恢复后状态真实可查。
12. 从备份恢复到隔离环境，记录完整且不自动执行任务或发送飞书通知。

### 16.2 必要的自动验证

- 领域测试：项目归属、授权版本、状态转换、暂停/停止与恢复约束。
- 存储集成测试：事务落盘、事件去重、Effects/Outbox 恢复和新 schema 迁移。
- 适配测试：不同资源环境、无 GitHub 项目、私聊跨项目回复关联、原生 Session 索引。
- HTTP 验证：受信任 origin 与认证正常，错误来源写请求被拒绝，实时连接可用。
- 故障注入：在记录任务、执行副作用、登记成果和发送通知的边界中断进程，检查恢复行为。

重用现有相关测试并补充关键行为验证，不通过镜像实现的测试证明正确。研究结论的科学有效性仍需用户审查，自动检查仅验证约定流程与可追溯性。

## 17. 书面评审重点与后续步骤

本规格把已确认方向落成可评审的边界。以下具体规则在书面评审中一并确认：检查点暂停、项目状态的数据库权威、首版保留旧历史而不全量自动迁移，以及每日备份、保留最近七份恢复点的默认建议。

用户评审通过后，进入 writing-plans，将三个增量拆成可执行的实施任务，并在准备阶段确定 fork、开发目录与 profile。现有 KORAM 服务在新闭环通过验收前保持隔离使用。
